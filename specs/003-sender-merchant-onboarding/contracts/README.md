## Identity amendment and channel compatibility

Customer registration starts only an individual Identity account, never an organization or grant. Candidate `/api/v1/customer-auth/*` isolates the new email-identifier transport from accepted exact-username `/api/v1/auth/*` and protected SYSTEM admission. Both call the single Identity account/security master. No Demo import/fallback. A server-assigned opaque username preserves existing exact username semantics; the immutable customer email-identifier binding is an additional Identity-owned lookup, not a rewrite/casefold of legacy usernames or legacy account emails. Email identifier comparison is exact NFC-independent code-point sequence with leading/trailing whitespace rejected, not silently normalized; alternate spellings cannot prove ownership. Public enrollment colliding with an existing verified identifier returns the same202; authenticated legacy linking/reverification is required to attach a new binding, never email-only takeover. No automatic import or implicit merge of old accounts.

Enrollment stores an Identity-owned pending enrollment with protected password material, intended account reference, versioned consent and24h proof. It must not insert an invalid PENDING_ACTIVATION row with a password contrary to V3 checks. Verification atomically consumes proof, creates/activates the one legitimate account using the existing valid ACTIVE invariant and establishes the verified email identifier; conflicting identifiers do not create a second master. Email link opens a no-store page with proof in fragment, strips fragment immediately, requires exact Origin/server-bound preauth CSRF and explicit POST confirmation; GET never activates. Raw proof never goes to query strings/logs/referrers/receipts. Proof locator compatibility is separately purpose-versioned; do not pretend current invitation HTTP locator mismatch is closed.

Enrollment/verification use separate purpose/key derivation from privileged invitation24h and recovery15min. Minimum32 random bytes, HMAC verifier, protected recoverable delivery intent/AAD and key lifecycle at least as strict as ADR0011; no plaintext proof DB/DTO/audit. Resend atomically revokes prior pending proof before issuing a new24h proof, rate limited and non-enumerating. Verification cannot claim delivery; user possession proof is still mandatory.

Customer login reuses accepted exact password validation (new minimum15 Unicode code points/maximum72 UTF-8 bytes; no trim/normalize/truncate, shorter legacy login remains compatible), RS256 trust configuration,900s maximum access,8h absolute/30min idle, backend revocation/authVersion, exact Origin/server-bound CSRF, strict rotating refresh/single-flight and replay-family revocation. No grace or blind retry after lost rotation response. Customer admission checks dedicated ACTIVE/verified customer binding, not protected SYSTEM grants; do not globally remove `eligibleRealm`. Accepted SYSTEM endpoints and full-target/union/self/last-admin checks remain unchanged. Distinct browser customer cookie/CSRF binding names and purpose prevent customer/system cookie confusion; same Secure/HttpOnly/SameSite=Strict/host-only/Path=/ protections and no browser persistent access-token storage.

Customer recovery request returns uniform202 for known/unknown/disabled/unverified identifiers, delivers only to stored verified security email,15min single-use proof; confirm atomically changes credential/revokes affected sessions/proofs/audit/receipt. Sensitive email change requires recent password reauthentication, proof to new email and notice to prior verified email; until consumption old email remains authoritative. Commit uniqueness and current-subject/version checks, then revoke sessions and require reauthentication. Phone is an optional business contact only. No phone authentication/recovery is implemented until a separately approved verified-phone adapter/proof contract; no account association based on phone possession.

Candidate limiter additions: enrollment5/identifier/hour+20/IP/hour; verification5/proof/15min; recovery request3/identifier/hour+20/IP/hour; recovery confirm5/proof/15min; security-contact change3/account/hour; Merchant invitation create/resend3/recipient/org/hour+20/actor/hour. Hash sensitive keys, reserve budgets atomically across instances, trust only approved source-IP policy, storage outage→503 not429. Existing accepted login/refresh/resend limits remain unchanged. These exact limits/config versions are pinned by the reviewed planning baseline; no modification to V6 in this task.

## Authority, locks, revocation and recovery

Customer/System cross-admission compatibility: the new customer transport uses a distinct configured customer issuer/audience/key ring and customer-owned session/refresh tables inside Identity, reusing the accepted Domain timing/rotation/security invariants. Existing SYSTEM verifier/refresh store never accepts or queries these families, including on an account that legitimately has both customer binding and existing SYSTEM privileges. Customer tokens cannot be used for SYSTEM admin APIs, SYSTEM/Demo tokens cannot be used as customer authority. Separate cookies alone are insufficient; token trust and refresh persistence both enforce separation. Identity still has one account/password/contact-verification master; this adds session purpose isolation, not a second Identity module.

`requestLegacyCustomerLink` and `confirmLegacyCustomerLink` are the only explicit exception routes accepting the existing current SYSTEM subject solely to attach that same account's verified customer identifier after intended-email proof. No body account ID, no SYSTEM grant mutation, no cookie-only legacy linking, no client-selected target. Public enrollment never guesses/reuses an existing account from email equality. Linking gives no business authority; customer session must then be established through its own transport. Candidate page `/personal/security/link-customer` is available only from the existing authenticated account settings. Legacy recovery/username behavior remains unchanged. Cross-domain token/refresh and authenticated-link/takeover fixtures are mandatory.

Identity disable/authVersion/security-contact/credential-reset protocol covers both session families under the same administration lock; new admission always rereads current account/authVersion. Old build after additive migration still rejects customer refresh tokens because it reads only accepted SYSTEM tables; legacy disable/version change immediately invalidates new customer admission too. New Identity-owned lifecycle adapters may coordinate storage for both purposes, without nesting an existing session-owned transaction inside the new bridge or weakening its rejection guard.

The customer_identifier relation is only a derived login index to the **existing authoritative Identity account security email**, not an independent contact-verification master. `verified_at` is proof-event metadata, never authority. Admission/subject/recovery require current account email_verified/activation, exact index-email equality with account.email and current version; stale index denies. Security-email change updates account contact plus index/versions and session invalidation atomically. Legacy link accepts only the current subject's exact already-verified security email plus proof; it cannot change security/recovery destination or accept an arbitrary new email. Ambiguous historical shared-email accounts never auto-merge/link publicly. This leaves one authoritative security-contact lifecycle; a customer business contact attestation does not overwrite it.

Candidate public `identity.api.customer.CustomerAdmission` owns the **new customer/business bridge transaction**. It rejects ambient transaction/synchronization/resources before entry, just as existing session commands do. It accepts only same-request server-verified principal/request binding; no caller-supplied actor IDs/booleans. `workflow` composes public Identity/Merchant/Pricing APIs; Identity imports no business module. A generic callback/opaque trusted admission capability permits business work without Identity knowing Merchant types. Existing `IdentitySessionCommands`/current-session store are NOT invoked inside that transaction; their current transaction-ownership guards remain intact. No broadening of `AuthenticatedActor`/Demo security/ArchUnit allowlists.

Same PostgreSQL DataSource, READ_COMMITTED, bounded lock/statement/transaction timeouts, no remote I/O inside TX. Fixed lock order: existing Identity administration/population lock → affected account UUIDs sorted → session UUIDs sorted → Merchant business-control population lock → organization UUIDs sorted → business-key lock → application/membership/invitation/receipt rows sorted. Public Identity API resolves/locks extra target subjects (applicant/transfer recipient) before callback from untrusted candidate references; Merchant rereads the immutable references and denies if changed. Never write Identity tables through Merchant/workflow SQL.

All relevant account disable/reset, customer security-contact changes and customer admission participate in the same Identity lock protocol. All org/membership/delegation/reviewer-scope changes, invitation acceptance and protected business commands participate in the same Merchant control/org lock protocol. Reviewer authority is a versioned Merchant-owned scoped Business Admin record for an eligible verified human, provisioned only through an offline Owner-authorized audited bootstrap/recovery procedure; no public self-grant, SYSTEM role shortcut or default reviewer seed. Bootstrap/revocation takes the same population lock and cannot approve its operator's own application.

After all locks, recheck account/session/time, current organization/member/reviewer/assignability, target revision/proof/policy and hold/obligation state. Stage business effect+audit+receipt/outbox; final admission/deadline checks immediately before commit define the authorization/commit decision point. Locks remain held through commit. A revoke that commits first makes later mutation deny (including stale-tab/replay); a valid earlier commit stays committed. Timeout/deadlock rolls back/no partial authority; retry only via an explicit same-key command after safe outcome resolution, never blind refresh retry. Account security mutations and membership revocation have separate effects: org revoke does not disable account or other orgs.

Approval creates org+exactly one initial Owner+application APPROVED+audit/receipt/outbox in the same owned local TX; IDs/initial Owner derive from locked verified applicant, never client Owner/account flags. Owner transfer is a two-step, expiring15min, target-bound proposal by current Owner and acceptance by eligible current target member with recent reauthentication; final TX activates new Owner before demoting old Owner atomically, checks versions and last-owner invariant. Recovery when no usable Owner requires two distinct scoped Business Admins, fresh representative proof and target-bound verified consent; requestor/approver/applicant/target separation and reason/audit required. Pending transfer/recovery grants no authority; cancellation/expiry/revocation invalidates proof. No generic bypass endpoint or unilateral Identity Admin recovery.

If future effects cannot join this local TX, persist ACTIVATION_PENDING with no ACTIVE org/member authority and an operation-scoped recovery record. Only a guarded finalization after all owner confirmations may activate. Compensation never deletes committed audit or bypasses authority. This package selects local atomic activation for current single-artifact/DB; introducing remote activation requires a separate exact amendment, not an implementation guess.

Idempotency: new mutation key binds current subject, operation, target, canonical input and original version; receipt replay rechecks current authority before returning safe original outcome, no repeat write/outbox/audit. Changed binding409, missing strong If-Match428, malformed400, stale412, state conflict409; unauthorized target404 before version/existence disclosure. Receipt retention minimum7d and at least applicable proof/recovery window, pending operations/holds exempt. No raw credentials/proofs in receipts. Lost business response resolves through scoped receipt GET; inability to resolve stays UNKNOWN. Meaningful activity follows the existing server-attested post-commit session-owned step; its failure cannot turn a committed business effect into a claimed rollback.

## State and business policy

Application transitions and org/member/invitation/transfer/evidence/delivery states are enumerated in policy.json; unlisted transitions deny. DRAFT → SUBMITTED freezes revision/evidence; reviewer takes SUBMITTED → UNDER_REVIEW; request-info → NEEDS_INFORMATION. Resubmit creates a **new immutable submitted revision**, retaining earlier evidence/decision history. Applicant withdraws only DRAFT/SUBMITTED/NEEDS_INFORMATION before approval. Reject/withdraw terminal records stay immutable; new linked application follows fresh duplicate checks. APPROVED is reached only with atomic org/initial Owner activation, never a direct PATCH status.

Initial sandbox entity types: COMPANY and HOUSEHOLD_BUSINESS. Both require nonblank registered name/legal identifier with declared issuing jurisdiction, registered and operating structured address text, applicant Identity reference (server), representative name/contact/relationship, representative authorization document, independently verified business email, supporting registration document, declarations of accuracy/representation and versioned privacy/review consent. This is a Capstone submission policy, not invented statutory/legal verification. Unsupported type rejects422. Business-contact verification uses an Identity purpose-scoped contact proof attestation; it does not change account security/recovery email or create another verification master. Pending proofs do not count as verified.

Duplicate key candidate: (jurisdiction,entityType,legalIdentifier), Unicode NFC/trim and ASCII separator removal only under versioned business policy; preserve original. No casefold/normalization of login credentials. One active application per business key; unique activated organization key. Ambiguous collisions return safe conflict/manual review, never merge organization or transfer Owner. Business-key changes create new reviewed legal-profile revision; contact/display changes cannot rewrite legal evidence. Facility addresses are business metadata, not confirmed serviceable pickup points.

Organization ACTIVE → SUSPENDED/→ CLOSURE_REQUESTED; scoped reinstatement returns ACTIVE; close only with current Orders/Finance/Pricing-contract/claims clearance held in the same coordinated local TX, no shipments/balance/contract/dispute obligations. No providers yet means clearance UNKNOWN: closure remains pending, not fake zero. Before downstream features exist, authoritative deployed owner must attest empty state with source/version; absence of module is not proof. Suspension denies business mutation/context; approved scoped history remains read-only. CLOSED never silently reopens or deletes history. Last valid Owner cannot leave/suspend/revoke/demote without atomic eligible replacement.

Owner permissions are scoped to org and its branches. Manager gets only explicit delegable subset (member.read/invite/manage within assigned scopes, facility/defaults edit), never Owner/legal-profile/financial/security/reviewer authority. Operator gets explicit operational read/settings rights only; Support only separately assigned support scope, not staff management. Business Admin review/org suspend/reinstate/closure/recovery rights are independent of Merchant membership; Identity Admin alone has **no** business authority (BC045 deny). Full replacement checks union of old/requested rights and every branch; no A-scope actor deleting B-scope rights. Assignable rights must be a subset of current actor delegable rights and approved role template; member cannot promote self. Pending invitations store inviter authorityVersion/org policyVersion; any inviter membership revoke/suspend or rights/policy change invalidates them, not automatic entitlement update. Resend creates new proof/version and revokes every prior active proof.

Draft creation accepts an empty/partial draft DTO so the applicant can obtain its server ID before scoped evidence upload. Submission/resubmission validates the complete ApplicationInput against the persisted draft and clean evidence under lock; an EmptyCommand cannot bypass required fields. Immutable submitted snapshots use the complete schema, not the partial draft schema. Business-contact confirmation returns an expiring purpose-specific attestation ID. Reauthentication returns a15min subject/session/authVersion-bound proof reference; submitted email must match the current subject and cannot select another actor. Recovery target first creates a15min org-bound OWNER_RECOVERY_CONSENT through their own verified session; two independent reviewers resolve that consent through Identity, revalidate representative evidence and atomically admit the target even when no old member remains usable. No client-supplied target account ID is trusted. A transfer demotes the prior Owner to the reviewed Manager subset in the same TX; recovery revokes unusable prior Owner memberships without globally disabling those accounts.

Legal-profile update creates a SUBMITTED immutable proposed revision and returns202; the current approved legal profile stays effective. Current Owner can upload private organization-scoped evidence through separate legal-evidence operations; current regional Business Admin ownership.recover can use the same endpoint for recovery-only quarantine intake when Owners are unavailable, without profile-edit/Owner/self-approval rights. Server binds staging bucket to org+actor+LEGAL_REVIEW or OWNER_RECOVERY purpose; max5 retained/reserved files per bucket, recovery references held. Former applicant status alone cannot upload for an organization after losing membership. Screening/download/quota rules are identical; at most five files per pending legal-review submission. Independent scoped Business Admin approval/rejection applies the new revision atomically with audit/receipt and cannot be self-review. Review If-Match binds the pending revision; baseOrganizationVersion captured at proposal is checked again under org/key locks, stale base409 preserves current approved profile. Changes to legal identifier/jurisdiction/entity type lock the old/new business keys and verify representative/registration proof with the same entity policy; a key already bound to any organization conflicts, never implies a takeover. Historical key-to-org aliases remain reserved; old approved application/evidence stays immutable. Pending/rejected changes never falsely appear externally verified.

## Evidence, delivery and retention contracts

Evidence POST is authenticated/resource-scoped multipart: one binary file and declared document purpose. Enforce at most5MiB/file/5retained-or-reserved files per application, concurrent quota reservation under application lock, content signature and parse validation for PDF/PNG/JPEG, no path/URL input, random server storage key outside public web root. Upload candidate writes private quarantine; approved scanner adapter returns CLEAN/REJECTED/UNAVAILABLE with digest/engine/policy version. UNAVAILABLE remains quarantined and reviewer/download denied, no fail-open or fake CLEAN. Replacement creates new evidence revision; submitted referenced bytes/digest immutable.

Private blob store and scanner interfaces are candidate adapters, not a vendor choice. Reviewer preview/download rechecks current authority, application/evidence state, screening result and digest each request; no public URL, redirect, unauthenticated link or raw storage path. Return attachment/no-store/nosniff/safe content disposition; never trust filename. Log only IDs/purpose/result, not file bytes, submitted PII, proofs or recipient addresses. Failed upload rolls back reservation and schedules owned orphan cleanup without exposing data.

Candidate email port: send protected intent with stable message ID, approved sender/recipient and purpose template via explicit configured SMTP adapter; secrets/TLS/auth/sender allowlist supplied by secret-managed deployment config. QUEUED→SENDING lease→ACCEPTED_BY_PROVIDER→DELIVERED only on verified provider delivery evidence (DSN/provider receipt) or recipient proof consumption tied to message; SMTP250 alone is not delivered. Transient failure→RETRY_WAIT with bounded exponential schedule up to5 attempts, never past proof expiry; permanent rejection→FAILED; expired intent→EXPIRED; key/adapter outage→BLOCKED, alarm and safe resend/recovery. Lease crash may duplicate delivery but never duplicate proof consumption. Worker decrypts only inside protected boundary, no body/proof logs. Sandbox SMTP/inbox evidence is labeled TEST, not proof of production email deliverability. No public Internet rollout authorized.

Retention clocks: draft inactivity from last successful user draft edit (reads/jobs do not extend); terminal evidence from REJECTED/WITHDRAWN terminal transition; approved evidence referenced by active org is exempt; audit from occurredAt.30/90/365 days are minimum sandbox candidates. Active review/request-info/appeal/dispute/legal/admin hold, active org/reference, unresolved command/recovery/financial/contract obligations block purge. **purgeEnabled=false**; initial job only emits redacted eligibility report. Destructive purge requires separate Owner compliance/config approval, dependency recheck+locks, secure blob deletion/key policy and metadata tombstone/audit; metadata not falsely marked deleted on blob failure. Restore quarantines recovered bytes, honors hold/tombstones and rechecks ownership/scanning; no resurrection of tokens or privilege. Fixtures test eligibility, not actual destructive purge.

## Minimum upstream contracts and frontend

Control-plane exceptions are explicit: a currently eligible Owner may request closure of a suspended org, and scoped Business Admin may reinstate/close/recover under the corresponding guards. Suspension still denies operational mutations and context use; these lifecycle controls do not silently reactivate it. Manager cannot manage an Owner or peer Manager, and no member may replace their own grant set to raise privilege. Identity disabling the last usable Owner is always honored; normal org authority then fails closed pending independent recovery as described in data-model.md.

BC159 consumes candidate `CatalogEligibility` from004 (service/coverage IDs, immutable version,effective interval,availability) and `ServicePolicyEligibility` from005 (service ID,policy version,supported flag,effective interval,organization eligibility). No price/rate calculation or catalog master in003. Workflow queries authoritative owners' public APIs at save under their publication/version locks, then Merchant persists only references and validated version. Missing/stale/unavailable/unsupported→409/503, never an invented default. Read API exposes last validated reference plus current availability without silently rewriting settings. Smallest sequence: implement the read/validate publication subset in004/005 and real owner fixtures before003 defaults; profile/application/member work is independent. Future publish withdraw invalidates use at next command; no promise that a historical default guarantees future shipment serviceability.

Org closure additionally requires Orders/Finance/Pricing/claims clearance; unavailable→CLOSURE_REQUESTED remains blocked. This does not block independent personal enrollment/profile/application acceptance, but full003 includes demonstrated safe pending/deny behavior. Successful closure across live obligations requires the real owner clearance subset, not all downstream logistics features.
