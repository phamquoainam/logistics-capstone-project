Customer/merchant account references are immutable UUIDs issued by Identity, validated through public admission/subject APIs under the shared lock protocol. No Merchant cross-module SELECT/UPDATE/INSERT into Identity. Identity does not physically delete referenced accounts; disabling is lifecycle state. Domain-local FKs and uniqueness enforce local integrity; cross-owner references are verified public contracts, not an invitation to write another schema. Optional cross-owner FK proposals require separate owner privilege review before DDL; not assumed here.

## Forward migration groups and compatibility

DB details required in the candidate migration: evidence `file_slot` CHECK1..5 with partial UNIQUE(application_id,file_slot) for retained/reserved/non-DELETED rows, allocated under application lock. Confirmed permitted deletion may release a slot; a tombstone alone cannot. Legal-review uploads similarly use a server-created staging revision/bucket, slot1..5 unique within that submission; all supplied evidence IDs must bind the same current organization/bucket before SUBMITTED. Existing reviewed buckets stay immutable. Organization stores an immutable initial-owner membership reference with a deferrable composite FK to that same org's membership, inserted within activation TX; unique approved_application/business-key registry prevents duplicate activation. All membership population mutations take the same org lock; a deferred DB constraint trigger checks that an operational organization is not left without an ACTIVE business Owner membership at commit. Identity account eligibility is separately enforced through the public locked protocol, never a cross-schema trigger/SQL query.

Security account disable must remain effective even for an Owner and cannot be vetoed by Merchant. If all business Owner memberships refer to currently ineligible Identity subjects, normal business authority fails closed with OWNER_UNAVAILABLE and only independent scoped recovery/history controls remain available. Server derives this from locked public Identity subject eligibility; it never pretends an ACTIVE membership row makes a disabled account valid. Recovery installs a verified replacement before normal authority resumes. Future enablement must test this case with old SYSTEM disable behavior and new customer admission, not introduce an Identity→Merchant compile dependency.

Current observed stream ends atV6. Additive only: no editing V1–V6, no repair, no Hibernate update, no Demo import/reinterpretation. Security lifecycle/old SYSTEM endpoints remain supported.
